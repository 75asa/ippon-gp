## 2. ネットワーク要件

### 2.1 同時接続数

| 端末 | 台数 | 接続先 |
|---|---|---|
| JUDGE | 10 | Firebase RTDB（WebSocket 1 本 / 台） |
| HOST | 1〜2 | Firebase RTDB + Storage（音声素材） |
| MAIN | 1 | Firebase RTDB + Storage（画像・動画） + PeerJS（シグナリング） |
| CAM | 1 | Firebase RTDB + PeerJS + MAIN への WebRTC（**上り最大 8 Mbps**） |

合計 13〜14 台。RTDB 側の同時接続数は Firebase の無料枠（100）で十分。

### 2.2 許可が必要なドメイン（社内 Wi‑Fi や会場のフィルタリングがある場合）

| ドメイン | 用途 |
|---|---|
| `*.firebasedatabase.app` | Realtime Database（投票・モード同期）。WebSocket（443） |
| `firebasestorage.googleapis.com` | 画像・音声・動画素材 |
| `www.gstatic.com` | Firebase SDK |
| `unpkg.com` | PeerJS ライブラリ（CAM / MAIN） |
| `0.peerjs.com` | PeerJS シグナリングサーバー（443 と WebSocket） |
| `fonts.googleapis.com`, `fonts.gstatic.com` | Web フォント（ブロックされても代替フォントで動く） |
| `cdnjs.cloudflare.com` | QR コード生成（`index.html` のみ） |

WebRTC は STUN のみで TURN が無い（#27）。UDP が全面的に塞がれているネットワークではカメラは繋がらない。

### 2.3 カメラ配信のネットワーク構成（優先順位）

画質はほぼネットワーク経路で決まる（#64）。CAM スマホと MAIN PC が **別ネットワーク** にいると上りが数 Mbps に縛られ、LED ウォールで「溶けた顔」「色の塊」になる。

| 優先 | 構成 | 補足 |
|---|---|---|
| 1 | **持ち込みルーターの 5GHz 帯に CAM スマホと MAIN PC を両方繋ぐ** | WebRTC が LAN 内 P2P で完結する。会場 Wi‑Fi は使わない |
| 2 | ルーターが無ければ **MAIN PC を CAM スマホのテザリングに繋ぐ** | P2P が同一端末内の LAN で完結する。スマホの電池消費が増えるので給電必須 |
| 3 | どちらも無理なら **HDMI キャプチャ**（#62） | CAM スマホ → HDMI アダプタ → USB キャプチャ → MAIN PC。WebRTC を通さないので電波状況に左右されない |

JUDGE / HOST は Firebase にさえ届けばよいので、会場 Wi‑Fi やスマホ回線（4G/5G）でも構わない。**カメラだけは同一 LAN にこだわる**。

### 2.4 会場 Wi‑Fi をカメラ経路に使わない理由

- **クライアント分離**（AP isolation）: 同じ SSID でも端末同士が直接通信できない設定が多い。TURN が無いので繋がらない、または繋がっても外部経由で遅い
- **混雑**: 来場者のスマホと帯域を奪い合う。帯域推定が絞られて解像度が落ちる（`qualityLimitationReason: bandwidth`）
- **キャプティブポータル**: 一定時間で再ログインを求められ、本番中に切れることがある

## 4. 当日タイムライン

### 開始 60 分前（設営）

- [ ] 持ち込みルーターを設置し、CAM スマホと MAIN PC を **5GHz** に接続（テザリング構成の場合は MAIN PC をスマホに接続）
- [ ] MAIN PC を HDMI でスイッチャー / LED に接続し、映像が出ることを確認。ディスプレイ設定は「ミラーリング」ではなく「拡張」推奨（HOST を別画面に出せる）
- [ ] MAIN PC / HOST PC の音声出力を PA に接続。PA 側で 2 系統（MAIN: OP 動画・お題読み上げ / HOST: SE）のレベルを合わせる
- [ ] MAIN PC の **スリープ・スクリーンセーバー・通知を OFF**。電源を接続
- [ ] MAIN で `ippon_main.html` を開き、右上「⛶ 全画面」を押す。素材の読み込みが終わるまで（数十秒）待つ
- [ ] HOST で `ippon_host.html` を開く。「読み込み中... n / N」のオーバーレイが消えるまで待つ
- [ ] HOST の画面を **一度クリック**（音声のロック解除）。その後「🔔 出題音」を押して PA から音が出ることを確認
- [ ] HOST 下部「🎵 音マスター」が **「マスター中」** になっていることを確認。なっていなければ「マスターになる」を押す（#23）
- [ ] CAM スマホで `ippon_camera.html` を開き「📷 カメラを起動」→ **LIVE バッジ** と「MAIN画面に配信中」が出て、MAIN に映像が出ることを確認
- [ ] MAIN PC で `chrome://webrtc-internals` を開き、解像度 1280×720 以上・`qualityLimitationReason: none`・ICE candidate pair が `host` 同士であることを確認（読み方は [REHEARSAL.md](REHEARSAL.md#webrtc-internals-の読み方)）
- [ ] HOST で「スコアリセット」「投票をリセット」を押して初期化。「待機モード」を押して MAIN が待機画像になることを確認

### 開始 30 分前（審査員対応）

- [ ] 審査員 10 名に `index.html` の JUDGE QR を配布。全員が `ippon_judge.html` を開き **座席（自分の名前）を選んだ状態** にする
- [ ] HOST で「採点モード」→ 審査員に 1 票ずつ試し投票してもらい、HOST 上部の票数が増える・MAIN のフレームが変わる・PA から投票音が鳴ることを確認 → 「投票をリセット」→「待機モード」
- [ ] 審査員のスマホの **自動ロックを長め（5 分以上）** に設定してもらう。スリープすると WebSocket が切れ、復帰に数秒かかる
- [ ] CAM スマホにモバイルバッテリーを接続。画面の自動ロックを「なし」に
- [ ] HOST の音量スライダー（左上）と PA のフェーダーで本番音量を決める

### 開始 10 分前（最終確認）

- [ ] MAIN: 全画面のまま、待機画像が表示されている。マウスカーソルが画面上に出ていない
- [ ] HOST: 「マスター中」表示。票数 0 / 6。スコア全員 0
- [ ] CAM: LIVE バッジ点灯、発熱していない、電池 50% 以上または給電中
- [ ] 審査員: 全員が JUDGE の投票画面（自分の名前が大きく出ている画面）を開いている
- [ ] PA: MAIN 系統・HOST 系統ともにミュート解除
- [ ] HOST から「▶OP MOVIE」を押す準備（OP 動画は MAIN 側で音が出る。HOST の SE と混ざらないよう PA の担当に伝えておく）

## 5. 進行手順（1 問あたり）

HOST の実際のボタン名で書いている。MAIN 側は RTDB の状態に追従して勝手に切り替わる。

| # | 段階 | HOST で押すボタン | MAIN に出るもの | 補足 |
|---|---|---|---|---|
| 1 | 待機 | **待機モード** | 待機画像 | 投票・公開状態も一緒にリセットされる |
| 2 | 出題 | **問1〜問6** のいずれか | お題画像 | 押すと投票がリセットされる。読み上げ音声は **▶1〜▶6** を押す（自動では鳴らない）。演出として先に **🔔 出題音** を鳴らしてから「問N」を押す |
| 3 | シンキング | **🎵 シンキング**（任意） | お題のまま | もう一度押すと止まる |
| 4 | 採点 | **採点モード** | カメラ映像 + 採点フレーム（0 票） | ここで初めて審査員が投票できる。回答者が回答したら押す |
| 5 | 投票 | （審査員が JUDGE で投票） | 1 票ごとにフレームが更新。6 票で IPPON 演出 | HOST から 1 票ごとの効果音が鳴る。HOST 上部の「票 / 6」で進み具合を見る |
| 6 | 公開 | **点数を公開** | 左下に点数バッジ（IPPON 未達の場合） | 6 票で IPPON になった場合は演出が出ているのでそのまま次へ |
| 7 | 加点 | 回答者名の下の **＋**（間違えたら **－**） | スコアボードは結果モードで反映 | IPPON 獲得者に +1。HOST の数字が即時に変わる |
| 8 | 次の回答者 | **投票をリセット** | フレームが 0 票に戻る | 同じお題で複数人が回答する場合はここへ戻って 4〜7 を繰り返す |
| 9 | 結果 | **結果モード** | スコアボード（顔写真 + 点数） | お題ごとの区切りやコーナー終わりで。次のお題は「問N」から |

### SE / アジェンダ系ボタン早見表

| ボタン | 何が起きるか |
|---|---|
| 🔔 出題音 | お題出しの前の効果音（HOST から再生） |
| 🎵 シンキング | シンキングタイム BGM。トグル式 |
| ▶1〜▶6 | お題 N の読み上げ音声 |
| 笑い1〜4 / 歓声 / 拍手 | SE。マスター端末だけが鳴らす。サブ画面のスマホから押しても PC 側で鳴る |
| 🔔 終了ブザー | コーナー終了のブザー。トグル式 |
| ▶OP COMMENT / ▶OP MOVIE | MAIN で動画を全画面再生（音は MAIN から）。もう一度押すと停止。終わると自動で元のモードに戻る |
| ルール説明 / 会場QR / 一般回答 | 対応する画像を MAIN に投影 |
| player1〜5 / judge1〜5 | 回答者 / 審査員の紹介画像を MAIN に投影 |
| P1〜P5 | 優勝者画像（P1 = player1）を MAIN に投影 |
| 投票をリセット | 票と公開状態を消す。スコアはそのまま |
| スコアリセット | **全員のスコアを 0 に戻す。本番中は押さない** |
| マスターになる | この端末を SE 再生端末にする |

画像・動画を投影中に「待機モード」「問N」「採点モード」を押すと投影は自動で消える。

## 6. トラブル時の代替手順

| 症状 | 対処（上から順に） |
|---|---|
| 審査員が投票したのに MAIN / HOST の票数が増えない | ① HOST が「採点モード」になっているか確認（お題表示中や公開後は投票できない）② その審査員に JUDGE をリロードして座席を選び直してもらう ③ 審査員サポートが JUDGE の「全員」画面から代理で押す ④ それでも駄目なら MC が口頭で票数を確認し、HOST の **＋** で手動加点して進行（採点フレームは合わなくてよい） |
| 音が出ない（投票音・SE） | ① HOST の画面を一度クリック（音声ロック解除は最初のクリックで行われる）② HOST 下部の「マスターになる」を押して「マスター中」にする ③ HOST 左上の音量スライダーが 0 になっていないか ④ OS の出力先が PA になっているか ⑤ 予備 HOST 端末で `ippon_host.html` を開き「マスターになる」 |
| 音は出るが OP 動画 / お題読み上げの音が出ない | これらは **MAIN 側** から鳴る。MAIN PC の出力先と PA の MAIN 系統を確認 |
| カメラが繋がらない / LIVE にならない | ① CAM の「⏹」で停止 → 「📷 カメラを起動」で再開 ② CAM スマホと MAIN PC が **同じ Wi‑Fi（持ち込みルーター）** に繋がっているか確認して繋ぎ直す ③ MAIN をリロード（→ 下記「MAIN がリロードされた」の手順も実施）④ HDMI キャプチャ経路に切替（#62）⑤ カメラ無しで **採点フレームのみ** で続行（フレームと IPPON 演出は出る） |
| カメラ映像が粗い / ぼやける | ① CAM の「⏹」→「📷 カメラを起動」（帯域推定がリセットされる）② スマホを Wi‑Fi に繋ぎ直す（会場 Wi‑Fi やモバイル回線に落ちていないか）③ CAM スマホが熱い場合は冷ます・他アプリを終了 ④ HDMI キャプチャに切替 ⑤ 採点フレームのみで続行。原因の切り分けは `chrome://webrtc-internals` の `qualityLimitationReason`（[REHEARSAL.md](REHEARSAL.md#webrtc-internals-の読み方)） |
| Firebase に繋がらない（HOST の票数が動かない・MAIN が切り替わらない・全端末で同時） | ① HOST PC / MAIN PC のネットワークを確認（ルーターの WAN 側が切れていないか。テザリング構成ならスマホのモバイル回線）② HOST をスマホ回線のテザリングに繋ぎ直す ③ 復旧しなければ **紙集計** に切替: 審査員は挙手、MC が票数を読み上げ、審査員サポートが集計用紙に記録。MAIN は待機画像のまま（または HDMI をスイッチャー側で別ソースに切替）。復旧後に HOST の ＋ でスコアを入力し直す |
| MAIN がリロードされた / Chrome が落ちた | `ippon_main.html` を開き直して「⛶ 全画面」。状態は RTDB にあるので **HOST で現在のモードのボタン（待機モード / 問N / 採点モード / 結果モード）を押し直す** と復帰する。カメラは `camera_room` を再監視して自動で再接続する（繋がらなければ CAM を停止→再開） |
| HOST がリロードされた | 開き直して画面を 1 クリック → 「マスターになる」。スコア・票数は RTDB から復元される |
| 審査員スマホがスリープして投票できない | 画面を点けて JUDGE を再表示（座席は選び直す）。復帰しなければ QR を読み直す。同じ座席を別のスマホで選んでも構わない（座席の排他は無い） |
| 同じ座席を 2 台が選んでいた | 票は 1 席 1 票なので二重投票にはならない。片方に別の席（会場審査員 1〜4 など空き席）を選び直してもらう |
| 誤って「スコアリセット」を押した | HOST の ＋ で各回答者の点数を入れ直す（結果モードで確認しながら） |
| 誤って「点数を公開」を押した | 「投票をリセット」で公開状態が消える。票も消えるので投票し直しになる |
| OP 動画が途中で止まる / 音が出ない | MAIN の素材読み込みが終わる前に押した可能性。HOST でもう一度「▶OP MOVIE」（停止）→ 数秒待って再度押す。MAIN 側は動画終了で自動的に元のモードへ戻る |

## 7. 既知の不具合と回避策

| Issue | 内容 | 本番での回避策 |
|---|---|---|
| #23 | HOST の起動時にスクリプトが途中で止まり、**PC が自動で音マスターにならない** | HOST を開いたら毎回 **手動で「マスターになる」** を押す。修正が入るまでは 4 章のチェック項目として扱う |
| #59 | CAM の「🔄 切替」（前後カメラ切替）を押すと解像度指定が消え、以降 **640×480** で配信され続ける | **本番中はカメラを切り替えない**。使うカメラ（通常は背面）を起動前に決め、切り替えてしまったら「⏹」→「📷 カメラを起動」で取り直す |
| #27 | TURN サーバーが無く、別ネットワーク間ではカメラが繋がらない | 2.3 のとおり同一ルーター / テザリングにする |
| #60 / #61 | 帯域が落ちると解像度が先に落ちる。コーデック未指定 | ネットワーク構成で防ぐ。粗くなったら 6 章の手順 |
| ARCHITECTURE 3.1 | 状態遷移が順序依存で、まれにモードが巻き戻る | 意図しない画面になったら目的のモードボタンをもう一度押す |
| ARCHITECTURE 3.1 | RTDB のセキュリティルールが無く、URL を知る人がスコアを書き換えられる | JUDGE 以外の URL を来場者に配らない。会場 QR は JUDGE のみ |
